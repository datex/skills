# Runtime Globals

Platform-injected globals available inside flow code. For *which* tier can call *what* (function ↔ action ↔ UI, datasource tier restrictions, storage access), see [calling-conventions.md](calling-conventions.md). This doc is the naming/shape reference; calling-conventions is the authoritative tier policy.

## Reference Table

| `$datasource` | Current footprint-datasource context (OData type). `.inParams` for declared inputs. Used inside the `value` of declarative `filters` expressions. **Note the singular** — different from `$datasources`. |

| `$shell` | **UI-tier only.** Package-scoped dialog primitives invoked from hub/grid/form/editor code. Built-ins: `$shell.<Package>.openConfirmationDialog(title, body, continueText, cancelText)` → `Promise<boolean>` (resolves to the user's choice); `$shell.<Package>.openErrorDialog(title, message)` for a simple error alert; `$shell.<Package>.showErrorDetails(title, message, error)` for an error with a details pane. Same `<Package>.<flow_name>` shape as `$flows`; the distinction is where the flow runs. Used for UI-orchestration helpers (file download, Excel export/import dialogs, clipboard ops, etc.) that must run client-side. |
| `$operations` | **UI-tier permission checks.** Package-scoped gate on named operations assigned to the current user's role set. Every registered operation exposes two Promise-returning checks: `.isAssignedToAll()` — true only when **every** role granted to the user carries the operation — and `.isAssignedToAny()` — true when **at least one** does; pick the one matching the gate's intent. Typically called from `on_init` / `on_apply_operations` grid or hub flows to disable toolbar buttons, hide add/delete affordances, or gate navigation. Generated shape: `IOperation { isAssignedToAll(): Promise<boolean>; isAssignedToAny(): Promise<boolean>; }`, one per operation. Polarity: assigning `Disable_<X>` to a role **removes** X; `Enable_*` call sites mostly use `isAssignedToAny`. Operations are declared in the package's `authorization` singleton (`configurationTypeId` **34**) `operations[]` and assigned via `roles[].assignedOperations[{name}]` — authoring and polarity: [authorization-editor](../authorization-editor/references/authorization.md#polarity). `$operations.<Pkg>.<Op>` resolves against that package's **published** release — see [Unpublished Cross-Package Surfaces](#unpublished-cross-package-surfaces) below. |

## `$utils` Helpers — Notable Semantics

**`$utils.isDefined`** — returns `false` for `null`, `undefined`, **and empty arrays/strings** (not just nullish values). This means a guard like `if ($utils.isDefined(errors)) { throw new Error(errors.join('\n')); }` correctly skips empty error lists without needing a separate `.length > 0` check. Do not "fix" these guards by adding length checks — the helper is intentionally collection-aware.

**`$utils.isDefinedTrimmed`** — stricter string-oriented companion to `isDefined`. In addition to the nullish/empty cases `isDefined` already handles, it also returns `false` for **whitespace-only strings** (e.g. `"   "`, `"\t\n"`). Use this when a string field is semantically required but users might submit blanks that pass `isDefined`. For non-string inputs it behaves the same as `isDefined`.

**`$utils.date` argument order** — the platform's actual signatures are `$utils.date.add(value, unit, date)` and `$utils.date.endOf(unit, date)`: the value/unit come **before** the date, the opposite of most JS date libraries (moment/dayjs-style `date.add(value, unit)`). Writing `$utils.date.add(someDate, 7, 'day')` compiles against loose typings but computes garbage — always put the amount and unit first.

**`$utils.http` tier availability and base URL** — available at **both** the action tier and the function tier. Unlike `$db`, an http call does not force logic down to the function tier. **But the two tiers do not take the same URL.** An action runs inside the Footprint runtime and may pass a relative OData path (`Orders?$select=Id`); a function runs in the cloud backend, has no implicit base, and must build an absolute URL from [`$settings`](#reference-table):

```typescript
const base = $settings.<Package>.FootprintApi.url;
const root = `${base}${base.endsWith('/') ? '' : '/'}Orders`;
const rows = ((await $utils.http.get(`${root}?$select=Id,OrderStatusId&$filter=...`)) as any)?.value ?? [];
```

A relative path in a function **compiles and validates**, then fails at runtime with `Invalid URL` — so `dxs configuration validate` cannot catch it, and neither can a validate probe. (This entry originally recorded only availability, established by exactly such a probe; the calling-convention difference cost a runtime failure on 2026-08-17.) Copy the pattern from a flow that already reads OData — `Utilities.get_uom_conversion_factors_flow`, `Allocations.get_location_coordinates_flow`, `SalesOrders.get_automation_candidate_orders_flow`.
**`$utils.isDefined` returns `false` for a `Blob`** — a `Blob` has no enumerable own properties, and `isDefined`'s collection-aware emptiness check treats an object with no enumerable properties the same as an empty array/string. A guard like `if ($utils.isDefined(blobValue))` skips a real, non-null Blob. Guard Blob-typed values with an explicit `!= null` check instead, and verify the guard with a direct log/inspection before adding more guards around Blob fields — the usual collection-aware behavior is actively wrong here.

**`$utils.isDefined` is not a TypeScript type predicate** — its signature is `isDefined(value: any): boolean`, not `value is NonNullable<T>`. Calling it does not narrow the checked variable's type for the compiler, so a strictly-typed call immediately after the guard (e.g. a `$db` `.equals(value)` predicate expecting a non-nullish type) can still fail to compile, or compile against the wrong inferred type. Use a plain `!value` check or an explicit assertion when the *compiler*, not just the runtime, needs to know the value is non-null. See also [flow-code-patterns.md](../datex-studio-shared/flow-code-patterns.md).

## Component `styles` — `IStyles`

The `styles` surfaces on cards, widgets, grids and forms are typed `IStyles` or a subclass that adds class setters (`ICardStyles`, `IFatNumberStyles`, …). The base members, from the generated global context: `setStyle(nameAndUnit, value)`, `removeStyle(name)`, `clearStyle()`, `resetStyle()`, `clearClasses()`, `resetClasses()`, `clear()`, `reset()`. A subclass setter called on the wrong type fails validate (`Property 'setGoodClass' does not exist on type 'IStyles'`).

## `$flows` Runtime Shape — Dynamic Dispatch

`Object.keys($flows.<Module>)` enumerates **`_`-prefixed snake_case backing fields** (e.g. `_some_function`) that are **not themselves callable** — invoking one throws `is not a function`. The callable member is the matching **un-prefixed** property, exposed as a non-enumerable accessor, so it never shows up in `Object.keys`, only on direct property access. Code that dynamically dispatches across a package's flows (enumerate, then invoke by name) must strip the leading underscore from each enumerated key and `typeof === 'function'`-check the un-prefixed property before calling it.

The Preview transport (an XHR to a URL carrying the flow name and branch) and the automatic `appId` stamp on storage rows written from Preview are recorded in [shell.md → `$flows` runtime shape](../shell-editor/references/shell.md#flows-runtime-shape-verified-live-in-preview).

## `$shell` Dialogs Ignore Escape

Every `$shell.<Package>.open<Component>Dialog(...)` dialog renders with `disableClose` semantics: a synthetic or real Escape keypress does not close it and does not resolve the caller's promise. The only way to close one is a click on the wrapper's own close button (which the hosted component's own close affordance also triggers under the hood). Keyboard-driven automation or hotkey design built on "Escape closes the top dialog" does not hold for these dialogs.

## `$shell` Package Scoping — Cross-Package Dialogs

The `$shell` injected into flow code is **package-scoped**: flow code in package A cannot see `$shell.B` at all — the property is simply absent at runtime, so a `Utilities` frontend flow probing `$shell.SomeOtherPackage` gets `undefined` even though the target component exists and is public. Symptom: dialog-opening code that works inside its own package "stops working" the moment the target lives elsewhere.

The proven cross-package resolution pattern (browser tier):

1. Probe **every package context's `$shell`** from the global context registry — `globalThis.registry.contexts` (the app context first). If the registry hasn't been populated yet, rebuild it lazily via a helper frontend flow before probing.
2. Fall back to `window.$shell`, then the injected `$shell`.
3. Resolve the opener dynamically off whichever shell exposes the module: `(shell as any)[module_id]['open' + component_id + 'Dialog']` — the `as any` cast is required because openers are statically typed. Use direct property GETs to test existence, with key enumeration as casing recovery (module casing varies).
4. Detect whether a generated opener expects an inputs argument via `Function.length` — do **not** string-match parameter names, which are renamed in minified production builds.

Wrap this once in a shared `navigate`-style frontend flow (taking `module_id` + `component_id`) rather than repeating the probe at every call site.

## Unpublished Cross-Package Surfaces

A typed or declarative reference to another package's member — `$flows.<Pkg>.<fn>`, `$types.<Pkg>.<Enum>`, `$operations.<Pkg>.<Op>`, a datasource/grid/hub reference by `moduleId` — resolves against that package's **published** release, not against any pending change on a sibling branch. A member that exists only on an unpublished branch of the referenced package is invisible to the consumer: the generated type doesn't include it, and flow code referencing it fails `dxs configuration validate` as if the member didn't exist at all.

This holds even when both packages are being edited in the same session — publishing the dependency (and bumping the consumer's package reference, a Studio UI step) is a precondition for any cross-package contract change, not an artifact of CLI staleness.

Error shapes enumerate the **published** surface, which is the tell that this is the cause: a `Property '<member>' does not exist on type '<Pkg>'` error whose generated type visibly lacks the member you just added on the dependency's branch.

Escape hatches, all with a cost:

| Approach | Cost |
|---|---|
| Publish the dependency, then bump the consumer's reference | The correct fix for anything meant to ship; requires the dependency owner's branch to be ready to publish. |
| Loosely-typed call (string literal matching a to-be-published enum value) | Decouples from the publish cycle at the cost of type safety — a typo compiles. |
| Same-branch edit (consumer and dependency share one package) | Not a cross-package reference at all, so the restriction doesn't apply. |

**Fail closed**: when in doubt whether a cross-package member is visible yet, treat an absence as "not published," not as "doesn't exist" — re-probe after the dependency publishes rather than concluding the member was never added.

## `$userSettings` — Per-User Settings

`$userSettings.<Package>` is the UI-tier runtime global backing a package's `userConfig` component (`configurationTypeId` 37) — the schema declares *what* settings exist; `$userSettings` reads and writes the *values* for the current user. Four Promise-returning methods:

| Method | Behavior |
|---|---|
| `.get()` | Returns the current user's settings object for the package, or a falsy/empty value if they never saved one — read defensively (`settings?.x?.y`), never assume the object exists. |
| `.set(value)` | **Full replace.** Overwrites the entire stored object. Spread the current value first (`set({ ...current, ...changes })`) or sibling settings are lost. |
| `.update(partial)` | **Merge, not clear.** Shallow-merges `partial` into the stored object — a key set to `null`/`undefined` in `partial` does **not** delete the stored key; the merge drops it, and the old value survives. Clearing a value requires `get()` → delete the key from the plain object → `set()` the result. |
| `.remove()` | Deletes the user's entire settings object for the package. |

The generated TypeScript interface is named `I<Package>UserSettings`, regenerated from the branch's `userConfig.settings[]` schema — flow code referencing a settings key the branch's `userConfig` doesn't declare fails `dxs configuration validate` with `Property '<key>' does not exist on type 'I<Package>UserSettings'`. A consumer component and the schema change it depends on must land on the **same branch**: the interface shape is per-branch, not a stable platform contract.

```typescript
// on_init — read defensively
const settings = await $userSettings.<Package>.get();
field.control.value = settings?.defaults?.warehouse_id ?? null;

// on save — read-then-set() full replace; update() would silently fail to clear
const current = (await $userSettings.<Package>.get()) ?? ({} as any);
const defaults: any = { ...current.defaults };
if ($utils.isDefined(warehouse_id)) { defaults.warehouse_id = warehouse_id; } else { delete defaults.warehouse_id; }
await $userSettings.<Package>.set({ ...current, defaults });
```
